Pino structured logs: requestId, route template, method, status, duration, safe error code; redact Authorization, cookies, credentials, message content. Audit separate, permanent business evidence. GET /healthz process liveness (no dependency); GET /readyz bounded DB SELECT 1 -> 503 if unavailable. Optional prom-client metrics: http_request_duration_seconds histogram by route/method/status class; http_requests_total; ticket_claim_conflicts_total; sla_breaches_total by priority/kind; jobs_runs_total by job/outcome; jobs_last_success_timestamp_seconds; db_up gauge. No ticket/customer IDs or content labels. Grafana panels request rate/errors/p95, claim conflicts, breaches, job failures and DB readiness; private monitoring profile, no public Grafana or metrics. Alert candidates job stale >2 intervals, DB unavailable, error spike; thresholds unverified. Deployment: provision Supabase DB + owner/runtime roles, apply migrations via direct TLS URL, seed synthetic data once, configure Render secrets, deploy API, verify readiness, deploy Vercel UI and same-origin proxy, check cookies/CSRF/HTTPS and all three incidents. Keep available seven days, verify host sleep and scheduler, document cold starts. Local compose persistent volume, pg_isready, API readiness, one-command run after environment setup. Recovery: stop mutations if compromise, isolate, rotate secrets/revoke sessions, preserve audit, inspect redacted logs, restore backup into isolated DB and verify counts/invariants, redeploy known good compatible commit. RPO/RTO not measured; record actual backup/restore timing, provider limits. Incident log: detected time, impact, mitigation, owner, recovery, follow-up. No live deployment or availability asserted.

## M6 operations as verified on the production-like container stack (local, 2026-11-22)
- Startup order: postgres healthy → one-shot `migrate` (owner role) → `app` (restricted role). The app refuses to start otherwise; `/api/readyz` also reports unsafe privileges and returns only `{ok:true}` / a generic 503 (no topology).
- Scheduler **without browser traffic**: with `SWEEP_INTERVAL_MS=5000` all SYSTEM invocations completed (START/FINISH audited), due breaches recorded and tickets auto-closed/expired, attributed to SYSTEM. No sweep stayed RUNNING.
- Restart evidence: app restart, `docker kill` (SIGKILL) and a PostgreSQL restart preserved data (15 tickets, users, audit rows grew only by real events); scheduler resumed; readiness recovered.
- Graceful shutdown: SIGTERM logs `shutdown: scheduler stopped … inFlightTickDrained` then Nest closes HTTP and Prisma and re-raises the signal, so the exit status is 143 (128+SIGTERM) — expected, not a crash.
- Logging: Pino JSON with request correlation ids; cookies/authorization/CSRF/idempotency headers redacted; errors reduced to `{errorClass, code}` — no raw dependency messages, no note bodies.
- Single-instance constraints: the in-process rate limiter is per instance (shared store is roadmap P1); the scheduler's DB lease/row-lock protocol is safe with multiple instances, but only one instance has been exercised. Prometheus/Grafana remain an optional M7 profile; the app exposes no metrics endpoint yet.
- Not demonstrated: high availability, backup/restore timing, disaster recovery, security compliance.

## M7 monitoring, alerting and recovery (local, 2026-11-22; details and evidence in docs/M7_EVIDENCE.md)

- **Metrics**: internal listener `METRICS_PORT` (off unless set; compose uses 9464 on `frontdesk_prod_monitoring_net`, not published), `Authorization: Bearer $METRICS_TOKEN` (required in production). Counters are process-local; durable totals are in PostgreSQL. Labels never contain ids, emails or text.
- **Start monitoring (optional)**: `node scripts/gen-env-prod.mjs` (adds METRICS_TOKEN / GRAFANA_ADMIN_PASSWORD if missing, never overwrites) → `npm run monitoring:up` → Prometheus `http://127.0.0.1:9091`, Grafana `http://127.0.0.1:3001` (user `admin`, password in `.env.production.local`), dashboard *Frontdesk — operations*.
- **Alerts** (`infrastructure/monitoring/prometheus/alerts.yml`, initial thresholds): FrontdeskDown (2 m), FrontdeskDatabaseUnavailable (2 m), FrontdeskHighServerErrorRate (>5% 5xx, 10 m), FrontdeskSchedulerInactive (no completed sweep > 5 m), FrontdeskSchedulerNeverRan (10 m after start), FrontdeskPersistentSweepFailures (≥3 in 15 m), FrontdeskSweepBacklog (moreDue for 15 m). FrontdeskDown was proven to fire. **No Alertmanager — nothing is delivered**; add one before relying on alerts.
- **Responding**: Down → `docker compose … ps/logs app`, readiness; DB unavailable → postgres health, credentials, startup privilege error in logs; scheduler inactive → logs `sla sweep finished`, `SWEEP_SCHEDULER_ENABLED`, lease recoveries; sweep failures/backlog → invocation rows (`SweepInvocation`), batch/lease settings, lock contention.
- **Backup/restore**: `bash infrastructure/ops/backup-restore-verify.sh` (owner-role pg_dump → `.local/backups/` 0600 → restore into `frontdesk_restore_*` + integrity/privilege checks). Roles must exist on the target (initdb script / managed-host provisioning); re-grant CONNECT. Restore into production = stop app → restore into a new DB → verify → repoint `DATABASE_URL` → start; never restore over the live database. Local timing only (0.66 s / 0.20 s for a 117 KB dump); no RPO/RTO claim.
- **Release build**: `npm run release:build` (from `git archive HEAD`) → `npm run prod:up:release`; verify the startup `commit` equals the intended SHA.
